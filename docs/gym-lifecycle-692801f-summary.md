# Gym Lifecycle and NeMo Integration Review

Commit `692801f` adds the versioned Gym lifecycle, NeMo adapters, format conversion, and a local CUDA acceptance script. It does not provide an isolated execution boundary, independent holdout custodian, or release authority.

## Public Entry Points

| Area | Entry points | Purpose |
| --- | --- | --- |
| Gym data | `load_gym_spec`, `resolve_gym`, `materialize_public_task_data`, `materialize_holdout_items` in [gym_data.py](../python/neural_foundry/gym_data.py) | Load bounded data-only specs and materialize split-specific prompt/target items. |
| NeMo | `load_mcqa_panels`, `simulate_arithmetic_mcqa`, `compile_public_nemo_dataset`, `import_successful_mcqa_rollouts`, `import_mcqa_preferences`, `train_mcqa_rollouts`, `train_mcqa_preferences`, `NeMoGymRunner` in [nemo_gym.py](../python/neural_foundry/nemo_gym.py) | Import MCQA panels, compile public splits, import runner artifacts, train SFT/DPO candidates, and reverify/evaluate runs. |
| Formats | `InteractionFormatRegistry` and registered message/tool/JSON converters in [gym_formats.py](../python/neural_foundry/gym_formats.py) | Convert supported interactions to and from NeMo request rows with schema checks. |
| Studio | `GymRegistry`, `WeightProgrammingStudio` lifecycle/Gym methods in [studio.py](../python/neural_foundry/studio.py) | Register models, Gyms, methods, lifecycle adapters, freeze plans, score attempts, run studies, and invoke NeMo operations. |
| Reward monitoring | `RewardDriftGuard` in [reward_guard.py](../python/neural_foundry/backends/reward_guard.py) | Stop on scorer-digest mismatch, invalid observations, reward/validation drift, or KL threshold breach. |
| Local run | `main()` in [run_gym_lifecycle_real.py](../scripts/run_gym_lifecycle_real.py) | Run the documented local Qwen/SmolLM lifecycle and bounded tool example. |

## What Tests Exercise

- [test_gym_job.py](../tests/test_gym_job.py) covers job validation, lifecycle state/lineage, split checks, reward drift, receipts, and restart/reload behavior. Its trainer, evaluator, and several model paths are test doubles; these tests verify contracts, not GPU capacity or endpoint identity.
- [test_nemo_gym_adapter.py](../tests/test_nemo_gym_adapter.py) covers panel import, shared WSP/LoRA data materialization, rollout and preference import, training receipts, candidate reload, and interaction-format conversion. Most training/evaluation behavior is fixture-backed or mocked; the tests do not establish independent holdout custody.
- [test_nemo_json_compiler.py](../tests/test_nemo_json_compiler.py) checks public split compilation and rejects holdout/non-JSON output before publication.
- [test_gym_validation.py](../tests/test_gym_validation.py) exercises the opt-in validation and receipt checks; passing it does not turn caller-reported responses into model-run evidence.
- The documented CUDA artifact run in [gym-lifecycle-v1.md](../protocols/gym-lifecycle-v1.md) uses real local training and reload, but explicitly approved caller-supplied teaching responses. Its validation result was 0/1 for each trained support candidate; the tool example passed its local verifier but remained incomplete.

## Mocked and Reported Boundaries

- Unit tests use in-process model, trainer, evaluator, and NeMo runner doubles. `RewardDriftGuard` tests validate stop logic, not the scorer implementation.
- The real lifecycle script uses local Transformers/PEFT training and local artifact reload. The support training examples are approved caller-supplied responses, not responses generated by the base model.
- The script's tool handler is a deterministic local lookup. The NeMo runner is a subprocess, but the model endpoint is user-managed; this is not a sandbox or vLLM serving-identity proof.
- The protocols keep `release_authorized` false and state that a local `owns_holdout` declaration is not independent custody.

## Holdout Blocker

`NeMoMCQAPanels.write_spec()` in [nemo_gym.py](../python/neural_foundry/nemo_gym.py) writes `to_spec_document()`, which calls `gym_spec_document()` in [gym_data.py](../python/neural_foundry/gym_data.py). That document includes every `holdout_rules` prompt and target. The CLI's `import-nemo-panels` path writes this spec, and [test_nemo_gym_adapter.py](../tests/test_nemo_gym_adapter.py) reloads the exported file. Therefore private holdout answers can leave the NeMo panel boundary even though public materialization rejects holdout. Do not use this export path with sealed holdout data until it is changed and covered by a regression test.

The protocol's holdout-custody language is a policy boundary, not evidence that the exported panel is isolated. The script's receipts also do not attest that a remote endpoint served the recorded checkpoint bytes.
